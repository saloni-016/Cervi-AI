CERVIAI: GITHUB ACTIONS, RAILWAY, NEON, AND GITHUB PAGES
======================================================

GitHub Actions builds and tests the CPU Docker image and pushes it to
GitHub Container Registry (GHCR). Railway runs that image and connects to
Neon PostgreSQL. GitHub Pages serves only the public landing page:

  https://saloni-016.github.io/Cervi-AI/
    -> Open demo on Railway (HTTPS *.up.railway.app)
    -> Invitation, sign-in, assessments and history in Flask
    -> Railway connects to Neon on the server

The address bar changes when you open the demo. GitHub Pages does not run
Flask or need app, database or deployment credentials. No custom domain or
cross-origin API calls are needed. This is an invitation-only educational
demo, not a clinical service. Use only invented form inputs, test accounts
and non-patient images you are allowed to use.

BEFORE YOU START

- Check your Railway plan and spending limits. Free allows 0.5 GB RAM per
  service; Trial allows 1 GB. Both have a 4 GB image limit. A passing build
  does not prove this PyTorch app fits those limits. In particular the ViT
  checkpoint and loaded model can both be in memory on the first image
  request. A restricted trial can also block outbound connections to Neon.
  If you accept paid hosting, Hobby starts at $5/month with $5 of usage
  included; more usage can cost more. Set usage alerts and a compute limit
  if available. Do not upgrade or start the service if you cannot accept
  charges. https://docs.railway.com/pricing/plans
- Railway can pull a public GHCR image. Private registry credentials on
  Railway require Pro. The package is separate from the GitHub repo and can
  be private even if the repo is public. Before making it public, confirm
  rights to redistribute the code, artwork and weights. Public disclosure
  is not reversible; do not make the repository public for this setup.
  https://docs.railway.com/builds/private-registries
- Each build fetches the ~343 MB ViT checkpoint through Git LFS. Check the
  repo owner's LFS quota. The container and Pages exclude archived uploads,
  but that does not remove those files from Git and its history. Review what
  is already tracked before sharing. Never commit keys, tokens or DB URLs.

STEP 1 - PUT THE RAILWAY FILES ON THE DEFAULT BRANCH

1. Review the changes on the change branch. Check for Dockerfile,
   .github/workflows/deploy-railway.yml, .github/workflows/deploy-pages.yml,
   deploy/deploy_railway.py and deploy/prepare_neon.py. The old Google
   workflow and scripts are no longer needed.
2. If the files are not on main, get the change branch reviewed and merged
   into main first. A workspace change alone does not update GitHub. The
   workflows are manual and run from the default branch. Merging does not
   deploy anything. Protect main and review Dockerfile, workflow, dependency
   and model changes before granting production deployment access.

STEP 2 - BUILD AND PUBLISH THE FIRST IMAGE

1. On GitHub, go to Actions > Publish CerviAI demo > Run workflow. Choose
   main and leave Update the existing Railway service UNCHECKED.
2. Wait for publish to pass; deploy should be skipped. The publish job
   verifies the LFS object, builds an amd64 CPU image, audits its installed
   Python dependencies, tests the web server and model artifacts, and pushes
   the tested image. In the run Summary copy Image tag, of the form
   ghcr.io/saloni-016/cervi-ai:<commit>-<run-id>-<attempt>. Use that full tag,
   not :latest or the separate registry digest reference. Do not reuse an
   image from before the Railway change: it did not enable Railway's hosted
   security checks. Don't overwrite a previously published tag.
3. In the repo or owner's Packages page, open the cervi-ai container and
   confirm it contains this tag and that Railway can pull it:
   - Public package: no Railway registry credentials are needed. If it is
     private, change visibility only if you have approved redistributing its
     contents. The image includes models and runnable code, not database
     contents, credentials or old uploads.
   - Private package: keep it private if needed. On Railway Pro configure
     read-only GHCR credentials directly in Railway's Registry Credentials
     settings (see the docs above). Do not put registry credentials in the
     app or share them in chat. If your plan cannot pull the private image,
     stop here instead of exposing it.

STEP 3 - PREPARE THE DATABASE ON NEON

Reuse the existing Neon branch and app-only URL if you already prepared them
for this demo. No migration from another host is needed. Otherwise:

1. In https://console.neon.tech, create a dedicated project (Neon Free is
   sufficient to start). Pick a region near your intended Railway region
   if practical. Use the intended branch and database throughout. Don't add
   a Railway database, enable Neon Auth, or upload your old database.db.
2. In Neon's Connect dialog choose the database owner, and turn Connection
   pooling OFF for this one-time setup. Copy the raw postgresql:// URL,
   not a psql command or surrounding quotes. Treat it like a password.
3. In a private local terminal, from a trusted checkout of the reviewed
   code, run the following (macOS/Linux; on Windows use the Python inside
   the virtual environment's Scripts directory). You can also download
   deploy/prepare_neon.py from GitHub and pass the downloaded file's path
   on the last line. This step does not need the model or Git LFS:

      python3 -m venv ~/cerviai-neon-setup
      ~/cerviai-neon-setup/bin/python -m pip install 'psycopg[binary]>=3.3.9,<4'
      ~/cerviai-neon-setup/bin/python deploy/prepare_neon.py

   Paste the direct owner URL at the hidden prompt. It will show the host
   and database. Type YES only if they are correct. The script creates the
   two tables and a separate cerviai_app login with read and insert access,
   not schema ownership. Do not create this login through the dashboard,
   which can grant it broader privileges.
4. Save the printed app-only URL in your password manager. It starts with
   postgresql://cerviai_app: and has a -pooler Neon hostname. Do not share
   the output or use the owner URL at runtime. If the role already exists,
   the script stops without changing it. If the app URL is lost, arrange a
   password rotation for that role with the owner, not a table/role deletion.

   https://neon.com/docs/connect/connect-securely

STEP 4 - START THE IMAGE ON RAILWAY

1. Create a dedicated Railway project (Empty Project). In the chosen
   environment (usually production), add a service from Docker Image and
   paste the Image tag from Step 2. Do not select GitHub Repo: Railway
   should pull the image tested by Actions, not rebuild the repository.
   Keep the project private. If the first attempt starts before you finish
   setting variables or registry access, it may fail. Apply the settings
   below before deploying again or publishing a domain.
2. In the service's Variables tab, add:

      DATABASE_URL    The pooled cerviai_app URL from Step 3
      SECRET_KEY      A random Flask session signing key
      DEMO_PASSWORD   A different random browser invitation password

   Generate the two random values separately, e.g. run this twice in a
   private terminal and save the outputs in your password manager:

      python3 -c 'import secrets; print(secrets.token_urlsafe(32))'

   Keep these values in Railway, not GitHub Actions. Seal the variables in
   Railway if available. Leave GROQ_API_KEY unset at first. If you enable
   Groq later, put its key there too; chat and combined explanations can
   send clinical text to Groq, though not raw image files.
3. In service Settings, before applying the deployment:
   - Keep the Docker image's Start Command (leave the override blank).
     Gunicorn binds to 0.0.0.0:$PORT. Let Railway set PORT and autodetect the
     target port. If you set an explicit target port, set PORT to the same
     value (e.g. 8080) so the healthcheck reaches the app too.
   - Healthcheck Path: /healthz. Use the default 300-second timeout to start.
     It is accessible without the invitation and becomes ready only after
     starting the app and checking Neon. It is not continuous DB monitoring.
   - Exactly one replica, in one region, and no volume. The image already
     uses one Gunicorn worker. Recent media and reports are worker-local.
   - Disable image auto-updates (if enabled) so only you or the GitHub
     workflow changes the tag. If your plan offers resource limits and your
     budget allows, start testing around 2 vCPU and 4 GB RAM. Measure actual
     usage before changing limits; these are not minimum requirements or a
     promise that the app will fit. For the first test, leave Serverless
     sleeping off if your plan allows it so startup issues are easier to see.
4. Apply/deploy the changes. Wait for an active successful deployment.
   Check Deployments and logs if it fails. In service Settings > Networking
   > Public Networking, Generate Domain. Copy the resulting HTTPS origin,
   e.g. https://cerviai-demo-example.up.railway.app. This is your app URL,
   not the github.io link. Don't publish Pages until it works.

   https://docs.railway.com/deployments/healthchecks

STEP 5 - VERIFY THE LIVE APP WITH DEMO DATA

1. Open your HTTPS app URL with /healthz appended. It should show ok with
   no prompt. Open the root URL in a private window. It should ask for an
   invitation (HTTP 401 without it). Use username demo and the invitation
   password, only on the exact Railway host. This is separate from Flask
   signup/login. If the root opens without an invitation in a fresh window,
   don't share the URL; check you're using the new image and settings.
2. Sign up with a made-up account, e.g. demo@example.invalid, and a separate
   password of at least 12 characters. Sign out and back in. Submit a
   synthetic clinical assessment and check History. An ordinary result
   refresh shouldn't duplicate it. Check the two tables on the intended
   Neon branch. The "public" schema does not make the database public.
3. Try Cell Image Analysis and then Combined Assessment with a small,
   authorized non-patient image (<10 MiB request; at most 16 million pixels).
   Check the class, heatmap and separate clinical and image results. Groq
   interpretation being unavailable is expected without its key. Check
   Railway CPU and memory during the first image request as well as at idle:
   /healthz alone does not load the ViT model. Temporary uploads, overlays
   and detailed reports can expire or disappear on a restart. Accounts
   and clinical score summaries live in Neon.

STEP 6 - LET GITHUB ACTIONS UPDATE THE EXISTING SERVICE

You can keep doing manual image tag updates in Railway if you don't want to
store a deploy credential in GitHub. For Actions-driven deployments:

1. In Railway's Project Settings > Tokens, create a project token scoped
   to the exact environment containing the demo service. Do not use a
   personal or workspace token. In the project canvas with that service
   selected, press Ctrl/Cmd+K and use Copy Project ID, Copy Environment ID
   and Copy Service ID. Use IDs, not display names.
2. In GitHub repo Settings > Environments, add railway-production. Limit
   its deployment branches to main and require a reviewer if available.
   Add the token as the environment secret RAILWAY_PROJECT_TOKEN, and add
   these three environment variables (or use repository Actions variables
   for the non-secret IDs):

      RAILWAY_PROJECT_ID
      RAILWAY_ENVIRONMENT_ID
      RAILWAY_SERVICE_ID

   The token authorizes deployments in that Railway environment. Use a
   project/environment dedicated to this demo. A person who can modify and
   run the workflow can deploy code that has access to its runtime data.
   Never paste the token into a file, command, or chat.
3. In GitHub Settings > Secrets and variables > Actions > Variables, add
   the *repository variable* CERVIAI_APP_URL. Use the exact HTTPS origin
   generated in Step 4. A trailing slash is fine; no credentials, query,
   custom hostname, port or /signin path. This public value is shared by
   the deploy checks and Pages. Don't put Neon or app secrets here.
4. Run Publish CerviAI demo on main again, now with Update the existing
   Railway service CHECKED. Approve the GitHub environment if prompted. The
   job checks the token scope and service, updates the image to the unique
   tested tag, waits for the new deployment ID to succeed and probes the
   public health and invitation endpoints over HTTPS. Both jobs should pass.
   Inspect the Railway deployment it reported and recheck History with the
   same test account. The workflow does not change Neon schema or secrets.
5. For subsequent releases, merge reviewed changes and run it again with
   the box checked. Don't edit the Railway source or start another deploy
   in the dashboard while this run is deploying. A failed or timed-out job
   is not proof nothing changed; inspect Railway's Deployments and source
   tag before retrying.

STEP 7 - PUBLISH THE DEFAULT GITHUB.IO LANDING PAGE

1. Make sure the app passed Step 5. Set the CERVIAI_APP_URL repository
   variable as in Step 6.3, even if you skipped GitHub-to-Railway automation.
2. In GitHub repo Settings > Pages, under Build and deployment set Source
   to GitHub Actions. Leave Custom domain empty. In Actions > Publish
   CerviAI landing page > Run workflow, choose main and run it.
3. When the Pages deploy passes, visit https://saloni-016.github.io/Cervi-AI/
   (including /Cervi-AI/). Check that its styles and image load and Open
   demo goes to the exact Railway origin. GitHub Pages should never ask
   for your invitation or account credentials. Share the invitation only
   with trusted testers. Rerun this workflow when the landing page or the
   Railway domain changes; it does not rebuild the Docker image.

TROUBLESHOOTING AND ROLLBACK

- No Run workflow button: enable Actions and verify the workflow is on the
  default branch. Check the publish job logs first. If LFS cannot download
  the weights, check the owner's quota and object at that commit. Do not
  bypass a failed dependency audit; review the advisory and package pins.
- GHCR push/pull denied: check the package's Manage Actions access for this
  repo, the exact image tag, and public or approved private-registry access.
  For private pulls, the credential belongs only in Railway Source settings.
- Railway startup fails: read the deployment logs privately. Check the three
  runtime variables, pooled app role and tables on the correct Neon branch,
  and outbound access to Neon on port 5432. The app requires verified TLS and
  channel binding; do not turn them off. On Railway it will not fall back to
  SQLite. A proxy 502 with a running worker can mean a mismatched target
  port. An OOM or timeout on the first image inference can mean insufficient
  memory or CPU even if the startup check passed. Check metrics before
  changing limits or plans.
- Actions deploy fails: check the correct Railway project token scope, the
  three UUIDs, the environment name, the domain and /healthz settings.
  Check the exact deployment ID in Railway. Don't treat the green publish
  job as a live release. If a new image is bad, use Railway's Deployments
  rollback on a known-good Railway image (can restore previous variables),
  or restore that image tag manually and redeploy using current variables.
  Neither rolls back Neon data. Do not revert to a pre-Railway image.
- Pages 404: confirm GitHub Actions is the Pages source, the Pages run
  passed, and the URL includes /Cervi-AI/. An invalid or changed app origin
  requires updating CERVIAI_APP_URL and rerunning the Pages workflow.
- Results expired or form expired: reload the form and resubmit a demo
  assessment. Detailed results and images are not durable. The unfinished
  Compare page is not a deployment test.
- To stop: take down the Railway service separately from unpublishing
  Pages. Disable the deployment workflow if unused and revoke its Railway
  token. Railway shutdown doesn't delete Neon data. If you previously set
  up another host, check and retire those resources separately to avoid
  ongoing charges. Removing vercel.json alone doesn't disconnect Vercel's
  Git integration; disconnect it in that project's Git settings if wanted.
